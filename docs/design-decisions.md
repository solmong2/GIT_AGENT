# 설계 결정 기록

설계를 검토하며 합의한 결정을 남긴다. 새 결정은 아래에 추가하고, 뒤집힌 결정은 지우지 말고 "변경" 표시와 이유를 적는다.

GIT_AGENT는 여러 저장소에 쓰는 공통 모듈이고 이 저장소는 public이다. 특정 대상 저장소의 정보(경로, 정책, 조사 메모)는 여기에 적지 않고, 추적하지 않는 `projects/` 아래에 둔다.

## 설정 구조의 확장 방식 (결정 11 상세)

- **층 쌓기**: 공통 기본값(`config/defaults.yaml`, 커밋) ← 프로젝트 설정(`projects/<이름>/project.yaml`, 로컬) ← 작업 정보(`tasks/<id>.md`의 앞부분 YAML, 로컬) 순으로 덮어쓴다. 새 항목은 기본값에 추가하면 모든 프로젝트에 바로 적용된다.
- **버전 필드**: 모든 설정에 `version`을 둔다. 형식이 바뀌면 읽는 코드가 옛 형식을 변환한다.
- **모르는 항목 허용**: 스키마 검증은 아는 항목만 엄격하게 보고, 모르는 항목은 경고만 하고 통과시킨다. 운영 중 항목을 먼저 적어 두고 코드를 나중에 붙일 수 있다.
- **영역별 묶음**: `agents`, `codex`, `tests`, `git`처럼 영역별로 묶어 서로 영향을 덜 주게 한다.
- **작업 정보는 md + 앞부분 YAML**: 코드가 읽을 값(기준 브랜치, 테스트 카테고리 등)은 앞부분 YAML에, 사람이 쓰는 설명은 본문에 둔다.

## Codex 경로 제한의 실제 강제 방법 (결정 12 상세)

- Codex 샌드박스는 쓰기는 작업 폴더로 제한하지만 읽기는 넓게 허용한다. "허용 경로만 보게" 하려면 프롬프트로는 부족하다.
- 방법: Codex 작업용 worktree를 **sparse checkout**으로 만들어 허용 경로만 디스크에 두고, 그 폴더에서 Codex를 실행한다. 작업이 끝나면 diff가 허용 경로 밖을 건드렸는지 코드로 확인한다.
- 민감 정보 분석이 끝나기 전에는 허용 경로 안의 설정 파일(예: 비밀번호가 들어갈 수 있는 설정)을 거부 목록으로 따로 뺀다.

## 검토 메모: Notion 연동

1. **작업 입력함**: Notion DB(작업, 대상 저장소, 상태, 우선순위)에 작업을 넣으면 오케스트레이터가 "대기" 항목을 가져가 처리하고, 상태와 결과 요약을 다시 적는다.
2. **검토 목록 화면**: `review_items.json`을 Notion 페이지로 보여 주고, 사용자는 댓글로 답한다. UI 단계의 대체 후보.

주의할 점:

- 상태의 원본은 저장소 파일이고, Notion은 보기·입력 창구로만 쓴다.
- 동기화는 LLM 세션이 MCP로 하지 않고 오케스트레이터 코드가 Notion API로 한다(MCP 호출은 매번 토큰을 씀). 스크립트용 Notion 통합 토큰이 따로 필요하다.
- Notion이 사내 워크스페이스라면 Codex(개인 계정)에는 Notion 내용을 넘기지 않는다.
- 시점: 검토 목록 단계가 생긴 뒤.
